# AI 充值赠送与退款本地验证

本文记录充值活动规则、资金实现、本地测试及上线切换要求，供后续维护和发布核对。

## 已确认规则

- 系统配置 → 其他配置 → 充值活动配置，可新增、修改、删除多个档位。
- 达到充值门槛后，按最高档赠送，不叠加。配置 50 送 5、100 送 20、200 送 50 时，充值 150 赠送 20。
- 支付订单实付仍为本金，赠送独立记录，并在创建订单时固定；以后修改活动不会改变已创建订单。
- 消费先扣全部本金，再扣赠送，同类资金按入账顺序使用。
- 任何金额的退款，均收回该笔充值尚未使用的全部赠送；赠送不能兑换为现金退款。
- 初始未配置活动，保留默认 10 元、自定义充值；示例档位不会自动写入正式配置。

| 充值与消费 | 退款结果 |
| --- | --- |
| 100 元本金 + 20 元赠送，消费 90 元，余额 30 元 | 最多退 10 元，同时收回 20 元赠送，余额归零 |
| 100 元本金 + 20 元赠送，消费 110 元，仅剩 10 元赠送 | 不可退款 |
| 未消费，退 100 元 | 收回 20 元赠送，余额归零 |
| 未消费，只退 1 元 | 收回全部 20 元赠送，保留 99 元本金 |
| 未消费，退 99.99 元 | 收回全部 20 元赠送，保留 0.01 元本金 |

## 资金与异常处理

迁移 `0092_ai_recharge_promotions.sql` 增加订单赠送快照、赠送余额缓存、退款收回金额及分笔账本。数据库使用用户行锁事务完成消费、充值和退款预扣，重复支付和退款通知不会重复记账。

退款先预留本金并收回赠送，再调用微信。超时、网络异常和不明结果保留预扣，并查询原退款号；确认不存在时只按原号、原实付参数重试。明确失败或关闭时，本金和赠送只返还一次；成功终态不会被迟到通知改回。

后台核实队列先筛选已到查询时间的记录，再取 50 条，避免旧退款挡住新退款。用户的防重复检查仍读取全部活跃退款。

历史余额按原流水重放，本来已有的总余额保持不变。历史金额或来源无法核对的账号只暂停自动退款，仍可消费和充值。历史退款流水与新流水分版本展示，避免把历史分桶变化误算成实际现金退款。

退款查询原则参考 [微信支付退款指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031) 和 [微信支付退款最佳实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)。

## 本地验证

- 后端：`go test ./... -count=1`、`go vet ./...`。
- 内存资金测试 13 组，覆盖消费顺序、部分退款全额收回赠送、失败返还、欠费抵扣、并发及溢出保护。
- 真实 PostgreSQL 资金、迁移与流水版本测试 10 组，另有退款队列测试 3 组。仅连接本机独立测试库，各测试使用独立 schema 并清理。
- 支付接口测试覆盖订单快照、客户端伪造赠送、重复到账、非法金额和以上退款示例。
- 退款通知及核实测试覆盖原号重试、金额与归属不匹配、旧未预扣退款、重复通知和迟到通知。
- 微信退款通知使用本地 RSA 测试密钥和 AES-GCM 报文，验证真实验签、解密、商户不匹配、伪造签名及错误金额；未访问真实微信支付。
- 前端：`pnpm test` 31 项、TypeScript 检查、`pnpm build`。
- 充值 UI 专项 8 项通过，覆盖活动选择、150 元最高档赠送、手机弹框、配置增删和其他字段保留、仅剩赠送禁退、支付记录与退款流水区分，以及历史版本 0 和缺失版本退款展示。
- 既有岗位、会员、支付和个人配置流程（59 项检查）通过。
- 既有“后台业务弹框和表格 24 项”流程在简历备注处失败：旧测试假定只有一个文本框，当前页面已有两个，且旧按钮名“新增备注”与当前“加备注”不同。该失败未涉及充值功能，未修改无关简历代码。
- 当前 Windows 环境无 cgo C 编译器，未执行 `-race` 仪器检查；内存与真实 PostgreSQL 均执行了实际并发测试。

## 发布切换要求

本任务只完成本地开发、测试及 Git 合并，未部署生产，也未操作正式支付和正式数据库。

上线时先停止旧后端写入钱包，再由新后端执行新增迁移并启动；不能让旧后端在迁移完成后继续按旧算法写入。正常数据库备份和迁移验证流程仍须执行。活动档位由管理员在上线后保存启用。
