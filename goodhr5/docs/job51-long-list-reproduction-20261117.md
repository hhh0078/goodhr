# 前程无忧长名单中断：先复现再修复

## 现场条件和复现

2026-11-17使用用户已登录的GoodHR浏览器（Mac6.3.4.5、浏览器152.0.4-beta.30），通过既有Go Browser Client调用唯一Worker。未注入脚本、未直连CDP、未点击打招呼或发送消息。

短名单50张时，启动约1.6秒，20人读取3.5至3.9秒。用真实滚轮加载750张后，启动约10秒，20人读取25至26秒。加载869张后，两次独立启动分别11.915秒、11.922秒报出与用户相同的WORKER_UNRESPONSIVE；最后请求仅730毫秒，浏览器仍连接且窗口未关闭。没有改超时参数或添加延迟。

原因已由现场验证：Go起点定位只有12秒总预算，却分成多次单元素查询；每次请求都重新截图测量自然窗口，名单变长后的重复定位和测量耗尽预算。

## 修复和同页对照

- 继续通过既有find-all封装能力，一次请求完成纵向名单的当前视口二分定位；同一请求只测量一次窗口，标准Locator只读边界，不读取上方姓名、不滚动或注入脚本。
- 保留原12秒预算、平台避让范围、当前屏幕首张完整卡片规则和后续行内身份核对。返回前检查名单总数和卡片边界；未知几何、旧Worker缺少协议、列表变化或空游标均不推进读取位置。
- 1000张真实卡片、同一静止页面上，旧逻辑再次11.920秒失败；新逻辑先连续10次成功（3.010至3.703秒），随后旧/新交替对比中又连续5次成功。
- 同页20人批次连续3次为36.090、37.114、35.817秒，未原样复现用户Windows的43秒超时。对实际测出的单次耗时，5人批次实测9.253、9.624、9.634秒。无忧配置按5人连续小批读取，保留原游标与滚动逻辑，不延长执行时限、不跳过不完整记录。不能把该性能对照写成已经在Mac复现了Windows的43秒异常。

## 回归与平台差异

公共Go与Worker没有新增系统专属调用；Windows amd64、Mac arm64/amd64使用同一实现。验证三端本地入口及Linux amd64/arm64服务器入口编译；Windows原机真实账号仍需验收，交叉编译不能代替Windows真机运行。

Worker全量377项中376通过、1跳过。新增覆盖869张二分定位、一次窗口测量、网格超高/横向越界卡片、名单和几何变化、无完整卡片和协议参数校验；Go覆盖单次只读协议、旧Worker、无效序号和空游标。BOSS、智联及无忧视口起点、后续批次与断点回归保留。

原始对照日志、请求编号、旧Worker摘要、诊断程序和截图保存在本机任务材料目录，不含真实候选人信息的源码才提交Git。没有将本次实验的临时工具、账号数据、Cookie或截图打入安装包。

真实连续读取回归：1000张卡片已加载的同一页面，从索引450开始，以5人为一批，调用正式平台FindCandidates和AdvanceCandidateList连续读取20人，用时52.475秒；逐人核对序号450至469，无重复、无漏号，最后游标465对应最后一批起点。单次完整字段读取约9秒，各请求保留原执行时限。
