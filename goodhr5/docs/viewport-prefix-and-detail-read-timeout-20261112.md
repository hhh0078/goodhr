# 当前卡片起点与简历正文读取超时

2026-11-12，用户确认取消无忧启动时的同名计数，并要求一并检查、修复其他平台同类问题。

## 日志能够证明的直接原因

排障快照 `dba68a6a4ff3fe9441a413a957303c186bc06075dd0fab4fed1caf697eedf123` 来自Windows amd64客户端6.3.4，浏览器152.0.4-beta.30，包含两类故障。

- 北京时间13:23:25结束的任务已经运行约29分30秒。结束原因明确是“同一操作连续3次出现相同错误”；连续失败步骤是读取无忧简历正文，原始错误为 `locator.innerText: Timeout 1500ms exceeded.`。保护策略以错误类型计数，读不到正文就不继续分析和发送；不是一到1.5秒便终止整个岗位，也没有证据证明浏览器已经断开。
- 13:40及13:41重新启动时，则在当前完整卡片几何定位之后回读屏幕上方人选，计算同名同龄出现次数。一批20人的读取耗尽起点检查剩余预算，最新请求预算7742毫秒、实际7786毫秒，报 `worker_deadline`。整个起点检查原有12秒上限，几何定位后只剩约8秒给额外读取；这与前面的正文单次1.5秒是两个时限。
- 日志还能看到网页自身脚本错误，但没有充分证据将它定为停止原因。正文为什么连续读不出来，可能涉及页面重绘、节点替换或浏览器繁忙；原始Windows现场没有在本机复现，不能仅凭一次超时把原因确定成网络加载慢，也不能承诺将时限改为5秒便消除全部页面故障。

- `StartCandidateViewport` 只探测数量、二分读取真实边界并复查起点几何，不再读取、计算或保存屏幕上方姓名及同名序号；起点仍是当前第一张完整卡片。沿用原来的整体12秒保护，不改成无上限等待。
- 视口游标及本批候选人标记为按真实行号核对。动作选择器先用原始卡片序号限定父级，再通过本地 `candidate.identity_check` 的标准 `:scope` 节点核对当前卡片身份文字；不把真实行号误当成“第几个同名者”。候选人换成另一身份时拒绝操作。沿用无忧公开编号解析和每次动作前的唯一性校验。
- 新方式只作用于正式视口起跑任务及其后续批次。分页、既有非视口断点、候选人去重、发送回执、失败停止策略、详情关闭及账户登录资料保持原逻辑，不建立失败回补队列。

- 其他元素、列表字段、聊天草稿及附件等原子读取默认值不变；请求取消、Worker队列与任务总时限仍可提前结束取值。真正读不到正文仍照常失败，不把空白当成功，不新增重发、点击或无限重试。
