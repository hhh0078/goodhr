# 生产发布与回收

生产构建从干净运行基础开始。禁止FROM任何历史业务成品，也禁止删除旧/app后再复制新应用。这类删除仅增加新层，无法移除旧层及父镜像依赖。

## 入口与阶段

正式入口为scripts/deploy-build.sh（发布命令在goodhr5目录执行）。auto_deploy.sh只拉取授权分支并准备候选，不切换线上。当前关闭的宝塔定时任务不会被此流程自动开启。

源码更新和正式构建共用goodhr5/.release-source.lock；手工快进同一工作区也须持有此锁及已有前后端部署锁。持锁后及镜像构建完成后再次核对HEAD和工作区，防止另一轮代码更新混入本次候选。

1. 核对目标服务器、源码提交、运行容器、迁移账本及空间。不要把代码合并当作线上切换授权。
2. 指定本次唯一GOODHR_RELEASE_IMAGE_TAG和GOODHR_DATABASE，通过--build-only构建。构建会拒绝已有发布目录或任一端已存在的版本标签；激活阶段复用原标签，不重新构建。
3. 在内网隔离网络中恢复完整数据库备份，关闭邮件、支付、外部Redis及后台调度。验证新镜像、当前迁移和旧数据保持，以及完整前后端回退组合。不得仅按日期挑回退，也不得把未经验证的旧后端与新前端拼接。
4. 保存下述隔离验收证据和兼容登记。核对候选image ID、源码、目标主机、基础镜像摘要及实际变更范围，取得生产切换和受限清理授权。
5. 通过同一标签的--activate-only激活已验收镜像。脚本不重建候选；先核对来源、标签、证据与实时迁移账本，再做完整数据库备份，只更新backend/frontend。
6. 健康检查成功后，自动生成本次临时目录清理计划、核对SHA执行，再重读实际Docker状态和兼容证据，按精确计划收回旧容器和镜像。失败停止并保留审计，不继续广域清理。

纯官网更新需要保留全部回退材料时，在激活前显式设置 `GOODHR_RELEASE_KEEP_ARTIFACTS=1`。该开关只跳过健康检查成功后的缓存、历史容器和镜像回收，保留本次发布材料及旧容器；构建、镜像来源检查、隔离验收、兼容回退预检、激活与健康检查仍全部执行。默认不设置时继续原有收尾流程。本次官网 SEO 发布使用此开关，保留所有回退材料；隔离演练创建的容器和网络仍须按其精确计划单独结束，不得使用全局清理。

激活使用 `scripts/release_activate.py` 读取当前 `goodhr-production-backend-1` 和 `goodhr-production-frontend-1` 的完整设置，只切换已验收的不可变镜像。旧环境数组的顺序和重复项、绝对绑定目录、监听端口、命令、资源限制及网络设置全部保留，不按新源码目录重建挂载。候选镜像新增的默认环境键按镜像顺序追加，安全日志只记键名；正式教程模拟开关必须为空，禁止使用43130/43131测试端口。镜像 `goodhr.*` 审计标签同步更新，其他既有标签保留。

helper只能由已持全部发布锁的正式入口调用。停止前再次检查干净源码、实时账本、候选镜像标签和当前容器配置，将原完整配置保存为本次目录的0600 `activation-originals.private.json`；该文件包含环境值，不得对外打印。旧对象停止后改名为 `goodhr-production-<角色>-1-backup-<本次标签>`，新对象在创建及启动后分别核对参数和健康。任一步失败会尝试把两个旧ID恢复到正式名称并启动；失败的新对象改为本次 `failed` 名称保留，不删数据库、镜像或容器。`activation-journal.json` 和 `production-result.json` 只保存身份及结果。成功之后仍由原发布入口完成健康检查和受限回收；初次上线没有这两个正式原容器时应使用单独审阅的初始化流程，不能冒用保留参数的更新入口。显式MAC仅支持唯一自定义bridge网络、无静态IP且Config与运行端点MAC一致的已审阅形态；停止时允许端点MAC被Docker暂时清空，恢复启动后重新严格核对。静态IP、多网络显式MAC、不一致MAC、匿名卷及自动删除容器会在停止前拒绝，需要单独审阅相应恢复策略。

示例（值必须由当前已核对目标提供，不照抄历史版本）：

~~~bash
export GOODHR_DATABASE=实际数据库名
export GOODHR_RELEASE_IMAGE_TAG=源码短SHA-唯一时间
bash scripts/deploy-build.sh --build-only
# 在隔离恢复库上完成验证并保存证据，然后：
export GOODHR_VERIFIED_RELEASE_EVIDENCE=/opt/goodhr-release/本次目录/isolated-validation.json
export GOODHR_RETENTION_REGISTRY=/opt/goodhr-release/retention-registry.json
bash scripts/deploy-build.sh --activate-only
~~~

正式构建文件用scripts/release_guard.py检查FROM，候选镜像再检查实际祖先链和业务文件层。scripts/release-policy.json仅登记已经核实无业务文件的固定运行镜像，以及回退数量。新基础需要重新核验版本、角色、文件和摘要后才能加入。goodhr.dockerfile_sha256必须对应实际构建文件原始字节；goodhr.source_commit、goodhr.release_kind、goodhr.release.id也须与候选一致。不要新增旧goodhr.release标签：经典构建器可能为每个标签产生中间镜像，引发来源误判。

正式前端构建默认将Node堆限制为1536MiB、Next.js构建核数限制为1；可通过 `GOODHR_BUILD_NODE_OPTIONS` 和 `GOODHR_BUILD_CPU_COUNT` 覆盖。两项仅作为Docker构建参数传入，不进入正式运行环境，低内存主机使用经典构建器时也会生效。

## 隔离验收证据

GOODHR_VERIFIED_RELEASE_EVIDENCE指向隔离验证成功的记录，而非尚未发生的生产切换结果。后者另存production-result.json。

~~~json
{
  "stage": "isolated_validation",
  "host": "已核对的生产主机名",
  "source_commit": "40位源码提交",
  "success": true,
  "legacy_data_preserved": true,
  "rollback_verified": true,
  "backend_image": "sha256:实际候选镜像",
  "frontend_image": "sha256:实际候选镜像",
  "before_migration_fingerprint": "隔离迁移前账本SHA256",
  "after_migration_fingerprint": "隔离迁移后账本SHA256"
}
~~~

指纹算法是所有schema_migrations.filename排序后，以ensure_ascii=False、separators=(',', ':')编码JSON数组，再对UTF-8字节做SHA256。激活前读取实际账本匹配before；兼容登记匹配after。无新增迁移时两者相同。存在迁移时，必须证明保留的回退组合兼容迁移后的数据库。

### 零迁移发布的通用隔离辅助工具

`scripts/release_rehearse.py run` 可在候选构建完成后生成本次专属证据。必须显式提供主机、源码路径/提交、发布编号/目录、库名、原前后端及PostgreSQL完整容器ID、候选前后端和Redis完整镜像ID；`--help` 不接触Docker。源码必须干净，工具持有正式发布同一组互斥锁，拒绝已有的 `本次目录/rehearsal`，不覆盖旧材料。

工具仅从明确生产库导出完整dump，并在新建的 `--internal` 网络和独立PostgreSQL/Redis内恢复；没有生产挂载、外部监听端口、SMTP配置或支付证书。候选和当前完整回退组合依次在同一恢复库启动，镜像内SQL集合必须与恢复账本完全相同。邮件调度关闭；退款和已读消息清理没有独立关闭开关，因此恢复库应用角色仅获SELECT，后台写入由数据库权限拒绝。public schema的CREATE只用于既有迁移表的 `CREATE TABLE IF NOT EXISTS`，不允许以此工具验证新增迁移。

恢复后的所有非系统表分别记录完整行排序SHA256和行数，迁移账本单独核验；两轮启动后均必须逐表完全一致，不能忽略退款、消息或系统配置表。工具检查健康、匿名私有接口401及前端页面200；报告明确标记 `read_only_startup_and_anonymous_routes`。本次功能的业务写入、AI协议、账务等仍须另有针对性测试，不能把只读检查当作这些功能已验收。

成功后生成 `本次目录/isolated-validation.json` 和 `本次目录/retention-registry.json`，内含候选与当前回退的完整配对证据。激活时显式指定这两个文件，不覆盖全局登记。无论成功失败均只停止本轮创建的临时容器，并在 `rehearsal/cleanup-plan.json` 登记精确id/name/image和网络ID，计划SHA记录于journal；核对后单独按精确ID移除停止容器及该网络，不使用force或-v，保留完整dump、恢复数据和证据文件。失败现场也须结束本轮应用和网络对象，恢复库数据目录保留排错，禁止交给生产finalize广域清理。工具本身不删除Docker对象、不切换生产、不执行回收计划。检查只在隔离环境实际运行成功后才可用于正式激活，离线单元测试通过不等于隔离演练通过。

### 显式0097文章单表迁移

默认命令仍只接受零迁移。唯一新增模式只允许已审阅的 `0097_public_articles.sql`，仅新增 `public.public_articles`、其主键和两个查询索引及中文注释。必须在原完整 `release_rehearse.py run` 参数之外，同时提供以下两项；不能把其他文件、多个迁移或任意DDL放入此模式：

~~~bash
--additive-migration 0097_public_articles.sql \
--additive-migration-sha256 已冻结文件实际64位SHA256
~~~

摘要应从本次已冻结的Linux源码文件读取，例如 `sha256sum cloud/backend/db/migrations/0097_public_articles.sql`；工具还会核对实际候选镜像内文件的原始字节，避免Windows换行或镜像漂移导致批准内容不同。候选镜像的迁移集合必须恰为原103个文件加0097，当前完整回退镜像必须恰为原103个文件；旧镜像并不要求包含新文件。

完整生产dump仍仅恢复到本次内部网络中的独立PG，不给候选提供生产密码、挂载、邮件或支付配置。候选必须通过真实 `RunMigrations` 启动执行0097，不能手工新增表或补账本来假装迁移成功。隔离应用角色仅在各次后端启动窗口获 `CREATE ON SCHEMA public`；候选额外临时获 `INSERT(filename) ON public.schema_migrations`，不给任何旧业务表写权限。`/health` 确认启动迁移结束后，马上撤销账本列INSERT，把新表所有者交还隔离管理员、只授应用SELECT，并撤销schema CREATE，再做其余HTTP和数据核验。旧镜像启动也有短暂CREATE窗口，因为既有 `CREATE TABLE IF NOT EXISTS schema_migrations` 在PG18仍会先检查schema CREATE权限；旧镜像始终不获账本INSERT，health后同样撤销CREATE。报告明确记载这些启动权限窗口，不能声称从未授予CREATE。

验收不能把迁移账本当作被忽略的表。本次原49表中，48张旧业务表的行数和完整内容摘要必须逐表完全不变；`schema_migrations` 的旧103行包括 `applied_at` 和其他字段必须逐行原样，仅允许追加0097这一行。新表必须是空表，其他表不允许新增或缺失。旧表字段、默认值、索引、约束、触发器、策略、所有者和注释保持一致；视图、函数、聚合、序列、自定义类型、命名空间、扩展及其他关系对象也不得出现额外变化。唯一文章表的字段集合、主键和两个指定索引另行核对。隔离角色的临时ACL变化单独核验，不作为业务DDL变化。

候选成功后，必须在**同一个迁移后恢复库**运行当前完整旧前后端回退组合。回退后全部50表的完整内容和104条完整账本、数据库结构都须与候选结束时完全一致，证明旧后端能保留并忽略新表及新账本。`additive-baseline.json`、`additive-migration.json` 和两个pair报告分别保留完整结构、旧账本和实际权限状态证据；最终 `isolated-validation.json` 的before指纹对应103条、after指纹对应104条，`expected_new_migrations=1`，两份兼容登记均绑定after指纹及实际镜像ID。既有正式激活与retention门禁已支持这种前后指纹不同的证据，不需要改宽它们。

此模式的匿名页面与只读启动检查不代替文章CRUD的独立HTTP/真实PG测试。现有自动迁移器在执行SQL后另行写入账本，不把两步声称为同一原子事务；0097采用可重复执行的新表/索引定义。任何阶段失败都保留本次dump、恢复目录和诊断材料，只结束本次临时对象；生产回退只恢复旧应用镜像，不能删除新文章表、账本或后来产生的文章记录。

## 回退登记和镜像回收

### 2026-10-26筛选记录的五份固定迁移

`scripts/release_rehearse_screening.py run` 复用通用演练的完整参数，仅接受0099客户岗位、0100消费汇总、0101向量回执、0102简历失效和0103筛选记录这五份明确SQL。候选镜像的旧SQL须与完整回退镜像逐字节相同；五份新增SQL的摘要须与本次干净源码一致，不能传入其他迁移或文章迁移例外。

完整生产备份先恢复到内网隔离PG；另建仅含旧结构、没有业务数据的参考库执行同一组固定SQL，推导精确结构。恢复库执行固定SQL后，旧业务整表摘要、完整旧账本及执行时间保持一致，只允许七张新空表及五条账本追加；实际全部DDL须与参考库完全一致。候选与完整旧前后端依次连接同一个升级后的恢复库，应用仅获SELECT；每次启动短暂授予schema CREATE以兼容PG18的既有迁移表检查，health后立即收回，不授予账本或业务写权限。失败也停止本轮应用并撤销CREATE。

报告明确标记 `fixed_image_sql_upgrade_and_read_only_startup`，不能将此过程声称为应用自动迁移或业务写入验证；自动迁移另以干净旧提交启动的真实隔离PG验证。通过后仍使用原激活门禁及本次专属兼容登记，不更改通用演练的默认零迁移限制。此版本的高级AI搜索默认关闭：服务端只有 `GOODHR_AI_SEARCH_ENABLED=1` 才允许助手、向量同步及向量接口；前端只有构建时 `NEXT_PUBLIC_GOODHR_AI_SEARCH_ENABLED=1` 才显示入口。现有岗位筛选不依赖该开关。

登记至少一套完整且与目标数据库兼容的历史回退；每端最多保留两份历史回退，另保护当前运行版本和完整配对的伙伴。数量不足时拒绝清理，不拿未验证版本充数。原始数据库备份、源码及安全回退二进制不随镜像清理。

retention-registry.json格式如下：

~~~json
{
  "schema_version": 1,
  "host": "已核对主机名",
  "current_migration_fingerprint": "目标迁移账本SHA256",
  "migration_probe": {"container": "postgres", "database": "已核对库名", "user": "已核对本地数据库用户"},
  "verified_releases": [{
    "id": "回退组合编号",
    "verified_at": "ISO时间含时区",
    "compatible": true,
    "migration_fingerprint": "相同迁移账本SHA256",
    "backend_image": "sha256:已验证后端",
    "frontend_image": "sha256:已验证前端",
    "evidence_path": "/opt/goodhr-release/本次目录/pair-summary.json",
    "evidence_sha256": "该文件实际SHA256"
  }]
}
~~~

pair-summary.json必须含host、success/legacy_data_preserved/contract_verified=true、backend_image、frontend_image和migration_fingerprint，逐字段对应登记，不能拿其他组合的报告或任意文件代替。

~~~bash
python3 scripts/release_retention.py check --registry "$GOODHR_RETENTION_REGISTRY" --evidence "$GOODHR_VERIFIED_RELEASE_EVIDENCE"
python3 scripts/release_retention.py plan --registry "$GOODHR_RETENTION_REGISTRY" --out /opt/goodhr-release/本次目录/docker-plan.json
# 审核精确清单后，使用输出的固定SHA：
python3 scripts/release_retention.py apply --plan /opt/goodhr-release/本次目录/docker-plan.json --sha256 实际计划SHA
~~~

plan不删除。apply持有与人工发布相同的部署锁，重查主机、全部容器/镜像快照、登记和证据摘要、实时迁移账本。只删除已列出的停止容器，不带force或-v；镜像按孩子到父亲、精确引用、--no-prune删除。运行服务、其他项目、外部标签及其依赖闭包永远保护。状态变化或删除失败立即停止并留下逐步审计。

三类构建阶段使用固定goodhr.project=goodhr及goodhr.build.stage标签，成功后才标goodhr.build.finished=true。每类最多保留最新一条已完成缓存分支及祖先；失败和过旧分支可进入本项目精确清单。禁止全局Docker prune，不影响其他项目缓存。

早期缺少标签的历史容器只能通过一次性的精确名单处理。legacy-allowlist.json包含schema_version、host、source_snapshot_path、source_snapshot_sha256，以及containers数组，每项为id、name、image、role；name保留Docker原始前导斜杠。来源必须是已核验的安全快照，当前实际三元、停止状态和明确的GoodHR镜像引用也必须相符。plan追加--legacy-allowlist 文件路径和--legacy-sha256 实际名单摘要，apply仍须使用最终计划SHA，并重读名单、来源和实时状态。此例外不允许处理运行容器、受保护回退镜像或其他项目；未来发布继续采用默认严格标记规则。来源文件路径变化后须重新生成名单和计划。

## 保持现有编译产物的运行基础迁移

仅在明确要求治理运行基础、保持应用产物不变时，使用release_cutover.py的只读plan生成专用计划。计划绑定主机、实际旧容器、已验证新镜像、原配置、备份新名、验收和操作代码摘要；不得作为绕过普通发布验证的入口。

审查计划后通过同一正式入口执行：

~~~bash
bash scripts/deploy-build.sh --runtime-repair --plan /opt/goodhr-release/本次目录/cutover-plan.json --sha256 实际批准SHA
~~~

专用迁移不提供镜像删除、数据卷删除或数据库写入功能；切换失败先尽力恢复原两服务，日志失败不能阻断恢复。验收成功后，旧版本仍须另外按release_retention.py的实时计划回收，不能在切换过程中强删。原容器被批准回收后，回退使用登记中已验证的干净镜像完整组合。

宝塔的“清理未使用镜像”也会删除尚未激活的候选和没有容器引用的回退镜像。发布期间只按精确清单回收；如已发生外部清理，必须停止失效计划，重新核对原运行服务、恢复候选并重新验证，不能只修改旧计划里的ID。本次验证通过的五个镜像另存一份完整压缩归档，校验镜像配置ID、层文件、压缩完整性及SHA，权限0600，作为误清后的恢复材料；恢复时先核对摘要，不直接运行未知归档。

既存GOODHR_CLOUD_ADDR覆盖已通过不启动的隔离容器验证：Docker API能逐项保留完整Env数组与重复项顺序。迁移仅按原样复制和严格有序比较，不转字典、不排序或删除重复项；其他未核验的冲突键仍会拦截。

## 临时目录与失败收尾

每次发布仅使用/opt/goodhr-release下独立目录。scripts/release_hygiene.py只处理该目录release-hygiene-manifest.json中明确登记且完成的白名单构建目录，支持先plan再固定SHA apply。succeeded/failed都可收尾已结束的构建缓存；失败恢复库保留排错。成功恢复副本还须有独立完整dump、可读TOC、原始摘要及通过的恢复报告，且无容器挂载引用。

~~~json
{
  "schema_version": 1,
  "host": "已核对主机名",
  "release_dir": "/opt/goodhr-release/本次目录",
  "status": "succeeded",
  "completed_workdirs": ["frontend-build/node_modules", "backend-build/go-cache"],
  "isolated_postgres": [{
    "path": "rehearsal-pgdata",
    "stopped": true,
    "container_ids": ["本次隔离实例ID"],
    "backup": {"path": "database.dump", "sha256": "原始dump实际SHA"},
    "rehearsal": {"passed": true, "report_path": "rehearsal-result.json", "report_sha256": "通过报告实际SHA"}
  }]
}
~~~

生产源码、public、.env、SQL、manifest、原始dump及回退文件不能登记为缓存。临时容器和网络必须由创建方结束；不会为清缓存停止线上服务。根盘少于6GiB或Docker分区少于3GiB时，正式入口提前停止。数据库备份暂不自动按期限删除，需单独审核保留或归档，不使用缓存收尾接口处理。
