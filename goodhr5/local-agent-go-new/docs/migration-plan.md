# 重构迁移计划

## 1. 总原则

- 旧项目继续可运行，新项目独立建设。
- 不整体复制旧目录。
- 每次只迁移一个可验证能力。
- 新项目不兼容旧项目中的错误边界。
- 先迁移通用能力，再迁移平台。
- 每个阶段通过测试后再进入下一阶段。

## 2. 不迁移内容

- Go 直连 CDP 实验实现。
- Node Worker 中的 Boss、猎聘、智联专用方法和路由。
- 超大 `index.js` 结构。
- 未验证的 `map[string]any` 协议。
- 构建产物、日志、PID、`node_modules` 和本地 `.DS_Store`。
- 重复实现的点击、输入和滚动。

## 3. 第一阶段：规范和骨架

- 建立 `AGENTS.md`。
- 建立目录说明、架构、Worker 设计和流程文档。
- 建立最小 Go module。
- 建立 TypeScript 严格模式。
- 建立格式化、类型检查和测试命令。

完成标准：

- 新目录职责无冲突。
- Go 和 Worker 的依赖方向明确。
- 不存在生产业务代码。

## 4. 第二阶段：浏览器协议

- 定义协议版本。
- 定义统一请求和响应。
- 定义 `SelectorSpec`。
- 定义 Worker 错误。
- 建立 Go 和 TypeScript 对应类型。
- 建立协议一致性测试。

完成标准：

- Go 不使用 `map[string]any` 调 Worker。
- TypeScript 不使用 `any` 接收请求。
- 非法请求能返回稳定错误码。

## 5. 第三阶段：TypeScript Worker

按顺序迁移：

1. 会话和 Profile。
2. 查找。
3. 移动。
4. 点击。
5. 输入。
6. 真实滚轮。
7. 文本和属性读取。
8. 截图。
9. Cookie 和下载。
10. 通用浮层。

完成标准：

- 原子能力无 HTTP 路由。
- Go 只能调用封装能力。
- 点击、输入和滚动有步骤日志。
- Worker 中没有任何平台名。

## 6. 第四阶段：Go 本地基础设施

- 配置。
- SQLite 和迁移。
- Worker 进程管理。
- Runtime 组件管理。
- Cloud、AI、OCR 客户端。
- Profile。
- 文件、端口、进程和防睡眠。
- 本地 HTTP API。

完成标准：

- 本地程序可启动。
- Worker 可安装、启动、健康检查和停止。
- API handler 不包含任务业务。

## 7. 第五阶段：任务框架

- 启动前检查步骤列表。
- 任务锁和取消。
- 主流程分发。
- 进度和日志。
- 主动停止和失败收尾。
- 本地状态恢复。

完成标准：

- 空平台也能跑通假的任务流程测试。
- 每个步骤有开始、成功、失败和耗时日志。

## 8. 第六阶段：第一个平台

建议先迁移 Boss：

- 入口页。
- 岗位选择。
- 候选人列表。
- 详情。
- 判断。
- 打招呼。
- 后续索要信息。

迁移旧 Node 平台能力时，应把“平台决定”移到 Go，把“通用动作”改造成 Worker 封装能力。

完成标准：

- Worker 中没有 Boss 命名。
- Boss 平台目录不包含通用鼠标实现。
- 真实账号完整回归通过。

## 9. 第七阶段：其他平台

依次迁移：

1. 智联招聘。
2. 猎聘企业端。
3. 猎聘猎头端。

每个平台沿用相同目录和 Runtime 接口。

## 10. 第八阶段：自动回复

- 建立独立 `auto_reply` 主流程。
- 平台新增消息相关接口。
- Worker 继续只提供通用查找、读取、点击和输入。
- 增加人工接管和重复发送保护。

## 11. 第九阶段：切换和清理

- 完成安装包。
- 完成 Windows 和 macOS 冒烟测试。
- 完成长时间运行测试。
- 对比旧程序数据迁移。
- 切换本地控制台到新程序。
- 稳定后再删除旧实现。

## 12. 每次迁移检查

- [ ] 迁移的是能力，不是复制整文件。
- [ ] 代码放在正确目录。
- [ ] 平台逻辑没有进入 Worker。
- [ ] Worker 原子能力没有对外暴露。
- [ ] Go 使用强类型协议。
- [ ] 选择器使用统一类型。
- [ ] 调用步骤平铺可见。
- [ ] 错误和日志完整。
- [ ] 没有 JavaScript 注入滚动。
- [ ] 有防回归测试。
- [ ] 未提交构建产物和敏感数据。
