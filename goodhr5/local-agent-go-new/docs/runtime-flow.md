# 本地程序流程

## 2026-11-10 当前详情策略与 OCR 停用范围

岗位详情识别由平台固定：BOSS 使用 AI，其余平台使用 DOM。后台表单不再展示详情方式选择，原 JSX 注释保留；历史 `ocr`、`ai`、`dom` 配置在云端读写、本地岗位快照和新手引导恢复时统一按平台兼容。公共 Go 入口是 `model.DetailRecognitionMode`，前端入口是 `positionDetailMode`，不能再用旧 `requires_ocr` 标志恢复本机 OCR。BOSS 关键词岗位需要 AI 详情时仍检查会员和 AI 配置。

当前运行组件只安装 Node 和 Camoufox。组件页、安装请求、预检、诊断和开发预览打包均不检查或下载安装 OCR。旧 OCR 源码、组件清单字段、安装记录和已下载文件保留，不删除用户文件；旧状态接口返回停用状态，旧识别接口返回 `410 OCR_DISABLED`。本文标注日期的十月 OCR 验证记录仅是历史依据，不代表当前仍启用。

自动回复的扫描附件由服务器 AI 图像能力识别，不在本机启动 OCR。本地手动导入入口暂未提供 AI 图片解析：遇到图片或扫描 PDF 明确提示改传文字版 PDF / DOCX，不能默默跳过页面或自动安装 OCR。三种系统共用此策略；本次已通过 Windows x64、macOS arm64、macOS amd64 编译和组件/兼容接口回归，Windows 与 Intel Mac 的实际安装仍需在对应系统验证。

## 支持的平台与运行组件安装

本地程序分别打包为 Windows x64 和 macOS（Apple Silicon、Intel）版本，公共安装流程必须兼容三个目标。

| 能力 | Windows | macOS | 实现位置 |
| --- | --- | --- | --- |
| 下载资源 | `win-x64` 清单 | 按芯片选择 `darwin-arm64` / `darwin-x64` 清单 | `internal/runtime/installer.go` 的 `platformKey` |
| Node 查找与安装 | 查找 `node.exe`，原地解压并检查版本 | 查找 `node`，保留 ZIP / tar.gz 的可执行权限与 `bin` 目录，原地检查版本 | `internal/runtime/installer.go`、`manager.go`、`node_executable.go` |
| Camoufox 查找与安装 | 查找 `camoufox.exe`，原地登记实际组件目录 | 保留 `.app/Contents/MacOS` 与 `.app/Contents/Resources`，检查执行权限 | `internal/runtime/component_paths.go`、`installer.go`、`manager.go` |
| 历史 OCR 源码保留 | 不执行查找、校验或安装 | 不执行查找、校验或安装 | `internal/runtime/ocr_retired_test.go`、`internal/api/ocr_retired_test.go` |
| 短命令执行 | 隐藏临时控制台窗口 | 使用普通可取消子进程，不引用 Windows API | `internal/runtime/command_windows.go` / `command_other.go` |
| 原生运行库 | 检查 VC++ x64 运行库 | 不执行 Windows 运行库检查 | `internal/runtime/system_runtime_windows.go` / `system_runtime_other.go` |

Node 和 Camoufox 使用免安装压缩包，不调用系统安装器。安装顺序为：下载、SHA256 校验、解压到独立 `runtime/node-runtime-*` 或 `runtime/camoufox-runtime-*` 目录、检查实际可执行文件与对应平台要求、原子写入 `installed-components.json` 的相对 `executable_path` 和 `directory_path`。Node 还须实际执行并确认主版本至少为 22。验证及保存成功后直接使用新路径，不再移动、覆盖或删除旧组件目录；重启时重新读取，目录整体迁移后相对路径仍有效。失败时清理本次新目录并保留旧目录与旧安装记录。旧固定 `runtime/node`、`runtime/camoufox`、系统 Node 和没有路径字段的历史记录继续兼容；历史 `runtime/ocr` 文件原样保留。已成功安装的目录不能当作临时目录清理；旧版本暂时保留，避免文件占用时清理失败影响本次安装。

Camoufox 的 `version.json` 写在实际组件根目录；Worker 的 `CAMOUFOX_INSTALL_DIR`、`CAMOUFOX_BINARY_PATH`、UBO、语言包、字体与浏览器原生资源补丁统一使用这个目录。Mac 中组件根目录是 `Camoufox.app` 的父目录，不能设成 `Contents/MacOS`。显式 `CAMOUFOX_BINARY_PATH` 仍优先，根目录按对应系统的应用结构解析。浏览器文件检查通过只能说明文件已安装，不能代表系统一定允许启动；真正的系统执行策略问题仍需启动日志确认。

历史 OCR 客户端的延迟构造与解析实现保留，当前所有业务入口均不调用它。组件更新不关闭用户正在使用的浏览器，也不触碰历史 OCR 目录。

Windows 的 `rename ... Access is denied` 只能确认目录移动被拒绝，不能单凭报错断言安全中心拦截；文件或目录占用、访问权限和安全软件都可能涉及。新流程减少对目录重命名权限及文件占用时机的依赖。若可执行文件本身仍被禁止启动，安装应在版本检查阶段明确失败，不能登记为可用。安装失败日志保留系统、组件、阶段、路径和原始错误，便于进一步区分原因。

回归要求：Windows 实际复现浏览器子文件被占用导致的 `Access is denied`，验证无需移动的新目录登记、旧目录被占用时的完整安装、版本文件被占用时保留旧记录；公共测试验证重启、目录整体迁移、ZIP / tar.gz、缺文件与模型、路径安全及实际 Node 子进程收到的浏览器环境。Windows x64、macOS arm64、macOS amd64 都需编译，Mac 可执行权限、双架构依赖与真机安装需在 Mac 验证。交叉编译通过不代表 Mac 真机验证完成。

## 1. 程序启动流程

```text
main
  1. 解析启动参数
  2. 加载本地配置
  3. 创建必要目录
  4. 检查固定端口是否已有健康的 GoodHR 实例
  5. 启用 10MB、3 份备份的本地文件日志
  6. 清理过期临时截图、组件压缩包和更新包
  7. 打开 SQLite、执行迁移、恢复异常中断任务并清理过期摘要
  8. 创建 Runtime Manager
  9. 创建 Browser Worker Manager 和 Client
  10. 创建 Cloud、AI、OCR Client
  11. 创建 Task Flow
  12. 注册本地 HTTP API
  13. 启动下载同步、服务和云端控制台
  14. 监听退出信号并按任务、服务、浏览器、下载同步、Worker、OCR、SQLite 顺序优雅清理
```

程序启动只保证本地服务可用，不应自动开始岗位任务。

固定端口已有实例时，必须先读取健康接口并核对状态、版本、端口和数据目录。确认是 GoodHR 后只打开现有控制台并退出；无法确认时不得结束占用端口的其他程序。

网页保持打开、本地程序在同一端口重启时，顶部旧连接状态不能代替本次进程的账号绑定。前端共享 `admin-api.ts` 的 `ensureLocalAgentReady` 在打开浏览器和开始自动回复前复用绑定接口，再串行等待浏览器启动检查；检查失败或等待期间账号变化时停止该次操作。后台状态轮询不重复绑定，停止任务也不等待组件准备。`internal/api/agent_binding.go` 对设备绑定后的登录校验失败返回真实错误，保持现有并发绑定代数与启动门闩，不持久化凭证。

前端通过 `camoufox_installed` 确认组件检查完成：`Manager.Status` 和 API 汇总都在 `StartupCamoufoxSyncPending()` 时将它置为 false。`camoufox_ready` 只在 Worker 在线并返回浏览器状态后为 true，不能作为首次打开的条件；现场冷启动允许 `camoufox_installed=true`、`camoufox_ready=false`、`worker_ready=false`。对应回归同时验证真实 Manager/API 的冷启动状态和启动门闩，不能只用浏览器已经运行的模拟状态。

2026-11-07 重连回归：前端 151 项单测、类型检查、本地 API race 测试及 Windows amd64、macOS arm64/amd64 编译通过。三个系统共用绑定接口和前端检查流程，无新增系统专属调用；同端口重启、等待后再打开、鉴权失败、检查失败和中途换账号使用隔离模拟接口验证。真实系统重启入口与安装包验收另行记录，交叉编译不代表 Windows 或 Intel Mac 真机验证。

## 2. 任务启动入口

所有任务统一进入：

```text
StartTask
  1. 解析强类型请求
  2. RunPreflightChecks
  3. 获取任务和 Profile 运行锁
  4. 保存本地 running 状态
  5. 同步云端 running 状态
  6. 启用系统防睡眠
  7. DispatchTaskFlow
  8. 返回已开始
```

后台流程必须持有可取消的 Context。

设备绑定检查成功后，必须把本次 `Checker.AgentBind.MachineID` 写入 `PreparedTask.MachineID`；失败时保持空。自动回复运行期间的 `credentials(prepared)` 只复用这份已核验快照，不能依赖 HTTP 启动入口先前取过设备编号。回归覆盖正式检查顺序、真实本机 HTTP 绑定响应与后续岗位列表的 `X-GoodHR-Machine-ID`，防止启动检查通过但循环第一次请求缺凭证。

## 3. 启动前检查

`RunPreflightChecks` 使用顺序步骤列表：

```text
checks = [
  ValidateRequest,
  CheckLocalProgram,
  CheckCloudSession,
  LoadPositionSnapshot,
  CheckSubscriptionWhenRequired,
  LoadUserPreferences,
  LoadLocalPlatformConfig,
  CheckProfile,
  CheckTaskConflict,
  CheckNodeRuntime,
  CheckWorkerBuild,
  CheckWorker,
  CheckCamoufox,
  CheckLocalStorage,
  CheckRequiredAI,
  // CheckRequiredOCR, // 历史步骤保留注释，当前不执行。
  CheckPowerGuard,
]
```

执行规则：

- 按顺序执行。
- 每步记录开始、成功、失败和耗时。
- 必需检查失败立即停止。
- 可选检查失败记录 warning，并明确降级结果。
- 返回完整的 `PreflightResult`，后续流程直接使用，不重复读取相同配置。
- 无 AI 需求的 DOM 关键词任务不检查 AI 或会员；BOSS AI 详情、AI 筛选及自动回复按实际能力检查会员。
- AI 岗位要求云端会员状态同时满足 `active=true` 和 `allow_ai=true`；自动回复还必须满足 `allow_auto_reply=true`，当前只有 Max 全能版开放。
- 本地检查是云端启动检查后的第二道保护，不能根据 `plus`、`max` 字符串自行推断权限。
- 平台 URL、行为和选择器只加载本地平台目录的 `config.json`，不请求云端平台配置；自动回复缺少消息地址或有效目标选择器时立即拦截。

## 4. 流程分发

```text
DispatchTaskFlow
  task_type=greeting   -> GreetingFlow
  task_type=auto_reply -> AutoReplyFlow
  其他                 -> UNSUPPORTED_TASK_TYPE
```

不同主流程不互相调用。

## 5. 主动打招呼流程

```text
GreetingFlow
  1. 启动或复用浏览器
  2. 打开对应 Profile
  3. 获取平台 Runtime
  4. 准备平台入口页
  5. 选择岗位并应用筛选
  6. 扫描当前可见候选人
  7. 检查运行中的云端登录态
  8. 后台并发执行候选人基础信息 AI 预判断
  9. 按页面顺序每 150ms 检查下一位预判断结果，完成一位立即处理一位
  10. 执行基础过滤
  11. 按个人配置等待并读取候选人详情
  12. 执行关键词或 AI 最终判断
  13. AI 流式 score、reason 完整后立即继续页面流程
  14. 收藏阈值大于 0 且详情 AI 分数严格大于阈值时，调用平台收藏能力
  15. 关闭详情并等待
  16. 调用平台打招呼能力
  17. 按最终 AI 分数决定是否索要电话、微信或简历
  18. 需要索要资料或发送首次招呼语时，优先复用聊天框或点击卡片“继续沟通”；首次消息才打开右侧联系人侧边栏
  19. 完成聊天动作后关闭聊天框和联系人侧边栏
  20. 岗位开启结构化简历时，后台接收 AI 剩余字段并异步同步云端
  21. 保存候选人结果
  22. 按个人配置休息、翻页或真实滚动
  23. 同步候选人发现数量、累计统计和最终状态
  24. 完成、停止或失败统一收尾
```

主流程只决定顺序。Boss、智联、猎聘页面差异由平台 Runtime 实现。

岗位 `ai_options.favorite_score_threshold` 默认 `0`，表示不开启收藏。公共流程仅使用已经打开详情后的最终 AI 分数，严格大于收藏阈值才在关闭详情前调用 `FavoriteCandidate`；等于阈值不收藏。收藏独立于“打招呼”开关和打招呼分数：只检查模式、未达到招呼分数时仍按收藏分数执行。关键词模式、没有详情 AI 分数或未打开详情时不收藏。Boss 和猎聘猎头端执行收藏，智联和猎聘企业端直接返回并继续流程；公共流程不按平台名分支。

收藏失败不记为成功，错误交给统一候选人错误策略；退出详情步骤时使用独立 45 秒预算补关详情，避免候选人取消或总时限已到导致弹窗残留。补关失败与原错误同时保留，会话失效和无法确认关闭的致命错误仍立即停止岗位。

收藏判断和详情清理共用一份跨平台 Go 流程，没有 Windows 专属路径或系统调用；Windows x64、macOS arm64、macOS amd64 都复用这里的规则。收藏页面差异只在 `internal/platform/boss` 和 `internal/platform/hliepin`，浏览器动作由共享 Worker 执行。`greeting/favorite_test.go` 通过合成详情和 AI 响应验证分数边界、招呼独立性、空操作及失败清理；它不代替 macOS 真机浏览器和安装包验证。

本次流程验证（2026-10-15）：`go test ./internal/flow/greeting ./internal/integration/cloud` 通过，`go test -c ./internal/flow/greeting` 分别以 Windows amd64、macOS arm64 和 macOS amd64 目标编译通过。macOS 仅完成交叉编译，真机运行尚未验证。

主动打招呼后的聊天动作必须留在推荐页：当前聊天框属于候选人时直接复用；不是首次消息且卡片已有“继续沟通”时直接点击打开聊天框，不打开联系人侧边栏；只有首次消息、卡片还没有“继续沟通”时，才点击推荐页右侧联系人入口并从侧边栏查找当前候选人。全部路径都不得跳转独立沟通页面。索要资料和发送消息共用同一聊天框，结束后统一关闭聊天框与可能打开的联系人侧边栏。

岗位选择的公共顺序为：读取当前岗位、必要时打开岗位列表、输入精简搜索词、读取结构化岗位项、点击匹配项、再次读取当前岗位复核。智联按旧版规则每次直接通过职位弹层选择搜索后的第一项，不读取不稳定的当前岗位文字，并验证弹层已经关闭；猎聘猎头端按旧版当前生效规则跳过页面切岗，只保存岗位上下文供开聊弹框使用。

需要 AI 详情时，Go 调用通用长截图能力。Worker 只用真实鼠标滚轮生成分段，截图交给 AI 识别；任何详情读取失败都会执行详情补关。智联和猎聘猎头端在 AI 判断前还会调用平台详情浏览能力，用真实滚轮模拟查看，不使用 JS 滚动。本机 OCR 分支保留源码但不可由岗位配置启用。

每批候选人开始前重新检查云端登录态。401/403 会停止任务；临时网络错误只记录 warning，避免短暂断网误停。个人配置中的列表停留、详情前后等待、打招呼前等待、滚动等待和模拟休息都使用可取消定时器；模拟休息只写本地日志，不修改招聘页面。

主动打招呼默认不限制扫描批数，不得再使用固定三批作为结束条件。每批完成后调用平台的统一候选人列表推进能力，持续加载下一批；只有达到岗位本次打招呼上限、平台确认没有更多候选人、用户手动停止、云端状态不允许继续或统一错误策略触发时才结束。若云端以后明确下发 `max_batches` 或 `scan_rounds`，才按该值限制批数。结束前必须写一条用户可见的原因说明。

候选人没有稳定编号时直接跳过，避免同一个人被重复打招呼。关键词岗位需要详情时，先读取详情再做最终关键词判断；多模态 AI 使用的临时截图在读取后立即删除。

基础信息 AI 预判断最多并发处理 5 位，但主流程始终按页面原顺序消费；第一位结果没回来时每 150ms 检查一次，第一位完成后立即处理，不等待整批。最终 AI 判断采用两段式流式消费：`score` 和 `reason` 完整后即可关闭详情、打招呼和处理下一位；岗位开启 `output_structured_resume` 时，剩余结构化简历字段继续在后台接收并异步同步云端，失败只记 warning，不回滚页面动作。

猎聘猎头端分页不依赖可能隐藏的“下一页”。平台 Runtime 从第 2 页开始，使用公共精确文本选择器依次点击 `2、3、4、5...`；每次点击后仍通过公共列表变化检测确认新候选人已出现。

## 6. 自动回复流程

```text
AutoReplyFlow
  1. 启动或复用浏览器
  2. 打开对应 Profile
  3. 获取平台 Runtime
  4. 打开消息页面
  5. 每轮检查云端登录态
  6. 扫描全部联系人并复核消息变化，不切换未读标签
  7. 读取会话上下文
  8. 判断是否需要人工接管
  9. 首次来信先读取在线基础资料或复用服务器同代缓存，再调用 AI 生成回复
  10. 执行发送前安全检查
  11. 调用平台回复能力
  12. 保存会话和回复结果
  13. 继续下一条或按间隔等待
  14. 完成、停止或失败收尾
```

自动回复不得复用主动打招呼的完整主流程，只复用明确的公共能力。

2026-11-10本轮自动回复以服务器为权威：聊天、目标、资料、发送账本和附件引用均写服务器，本机只执行浏览器动作及保留本轮临时材料。BOSS在线资料复用既有Worker长截图及公共拼图，截图交服务器AI后不作为候选人长期数据保存；猎聘使用可见DOM。首次在线基础资料与真实附件分别记录，在线资料不能冒充已收到附件。无完整手机号的在线临时资料采用30天维护清理接口，真实平台沟通可续期，查看、轮询与重放不能按当前时间续期；接口、鉴权、匹配及边界见[《BOSS自动回复与在线临时简历》](../../docs/BOSS自动回复与在线临时简历.md)。

BOSS通过明确平台行为将出站正文在服务器Claim前定为单行，登记意图、设备草稿、回执核对使用同一份正文；禁止发送后通过模糊压缩空白冒认回执。猎聘在线DOM弹层隐藏原聊天的行为由`auto_reply_online_profile_hides_conversation`单独配置，仅本次从已核实原生身份入口实际打开后临时允许聊天缺失，关闭后必须恢复并重验原生编号。姓名缺失先短探测，存在才读取，上限600毫秒，不反复等待原配置的3秒；BOSS不适用此DOM例外。

现有平台配置继续使用 `conversation_fields`，读取时由 `internal/platform/common/reply_fields.go` 按节点用途选择字段，禁止把整份混合字段交给每条聊天消息。联系人读取姓名、头像、摘要、未读数字、会话编号、候选人/招聘账号编号、性别和岗位；消息读取方向、正文、时间、消息编号、简历/通用/附件卡片和卡片候选人编号。`id`、`candidate_id` 属于两类解析器都会使用的后备字段，两边保留；`text`、`sender_role`、`item_class` 等旧消息字段也保留。新增解析字段时应同步维护该集合及真实平台配置回归，选择器本身仍由各平台配置提供，Worker 不判断平台。

这一分组同时用于未读扫描、按稳定编号重新定位联系人、完整/差量历史及最新消息读取。消息节点不再读取联系人 `name`，避免不存在的姓名触发补读与大量错误日志；五千条上限、取最新端、真实滚轮及身份核验规则保持不变。回归覆盖 BOSS、猎聘企业端、猎聘猎头端、智联配置；前程无忧不在本次实测范围。

猎聘历史加载由 `liepin/reply_messages.go` 每轮只读首尾消息编号及总数；纯滚动不重复解析全部正文，确认边界后再完整读一次。向上每轮真实滚轮距离1600，沿途等待300ms，首条已可见时等待800ms；连续三次首条可见、无位移且首尾/数量不变才确认顶部。回最新端使用距离2400，末条已可见则不再滚动，并再次核对末条序号与总数。全程仍共用两分钟预算，不削减记录，也不通过脚本改滚动位置。Windows和Mac均使用相同标准滚轮接口及实际几何反馈；本次Mac观察到的约二分之一CSS位移仅是现场结果，不作为其他系统的倍率假设。合成回归覆盖20→40→60→89条累计加载、已知边界、5000条截尾、异步插入及取消，真实往返耗时仍以实测记录为准。


猎聘普通聊天行没有可读的平台消息编号时，使用方向、类型、正文和归一化分钟，再按完整分钟组内同文出现次序区分；第一条保持旧指纹，后续条目使用独立指纹。最新消息尾窗必须向前覆盖到更早分钟或已加载 DOM 的起点，不能把一条尾窗当作完整重复组。历史加载在真实顶部尚未确认时，不用首分钟无编号消息作为已知停止边界；5000 条截尾首组无法确认时不提交其猜测编号，其他完整组仍可同步且不宣称完整。若当前已读窗口发现旧版本合并过的重复组，连同其后原始顺序锚点一起幂等同步，新增历史行标为 `history_backfill`，不产生待回复。旧版本已漏存的更早记录由消息标识版本触发一次完整重采：任务启动时仅登记当前账号、启用岗位及限定候选人范围，成功到顶且同步有旧消息锚点后原子升级版本；失败保留待办，完成后恢复增量读取。合成回归从 87 行读取并补齐到 89 行，验证两次同步不重复插入、顺序不变、原待答数量不增。

简历采集与补审待办存在服务器会话的 `resume_retry` 中，不依赖平台未读。每次浏览器或模型调用前先事务领取，最多自动三次，十分钟租约防止重启后立即重复调用；失败后退避一分钟、两分钟、四分钟。第三次仍运行时不能被人工重置；失败或租约过期后，可由已认证当前账号的重试入口重置耗尽项，不修改已发消息。普通会话保存保留待办，只有显式完成或补审事务可以清除。结构化候选人同时保存 `resume_source_message_id`，新附件不能复用旧来源的成功标记。无新聊天的补审核对来源、完整简历版本、最后候选消息及岗位版本，并一次提交确认项、新推荐收据和待办完成；不调用发送。

以上编号和重试逻辑共用于 Windows x64、macOS arm64 和 macOS amd64，无系统专属调用；事务在服务器内存投影执行并提交PostgreSQL，本机不保存权威业务数据；编译由最终候选统一执行。真实验证只覆盖本次 Mac 隔离环境，跨编译不代表 Windows 或 Intel Mac 安装、浏览器交互已经实测。

简历待办可先通过 `EnqueueAutoReplyResumeRetry` 登记（次数为零、无租约），问答不必等待旧附件；真正采集时才领取次数。`Behavior.AutoReplyResumeLoadsHistory` 默认关闭，仅猎聘开启：公共流程跳过预先寻源，由 `CollectAutoReplyResume` 内部使用标准附件入口探测、首尾轻读和真实上翻。卡片出现后才完整读一次核对来源，保持当前位置进入既有附件滚轮，不先返回聊天底部。模拟 20→40→60→80 加载只读一次完整字段，错源、取消和到顶无卡片均停止；其他平台默认行为不变。

猎聘简历采集以真实附件为首要来源：下载记录为 `saved` 且本地文件存在、非空后，确认附件预览已关闭、任务未取消并核对原聊天框，直接返回文件与可读的附件正文。公共流程负责解析文件、提取联系方式和结构化；页面正文为空不影响文件解析。已取得附件后不再强制打开在线简历，避免补充资料耗尽预算而丢弃附件成果。首次来信的独立在线基础资料现已前置读取，不能把它冒充附件或当成下载失败的替代文件；卡片缺失、下载失败、关闭失败和身份不确定仍返回错误并保留待办，不生成占位简历或报告。该顺序不依赖操作系统，Windows x64、macOS arm64 与 amd64 共用同一实现；回归使用临时真实文件验证文件返回、在线入口不调用及取消/关闭/身份错误边界，真实招聘页面由后续隔离实测确认。

附件出生年月沿用 `BirthYM` 的 `YYYY-MM` 格式。原文在“出生日期”“出 生”“DOB”等标签旁给出唯一年月时，保存该年月及 `BirthYMPrecision=month`。模型遗漏年月也可从这个标签恢复；模型与原文冲突、多个不同的生日、只写年份、仅有年龄或工作教育日期时留空。已有的年份估计不会升级为明确月份。

复用已结构化的旧简历时，正常新消息先完成回复；已读会话也可在再次核对时补全。程序仅使用服务器保存的原文，在服务器事务内核对会话归属、候选人、原文、简历来源消息和附件引用，且生日和精度仍为空才写入。成功补齐后，岗位已授权时才同步结构化结果。此路径共用于 Windows x64、macOS arm64 和 amd64，不重新下载附件或调用简历模型。

简历采集使用独立的 90 秒补处理预算，包含冷历史定位、下载、关闭预览及恢复原聊天框；消息问答已在前轮完成，不等待这一步。第 11 轮 Mac 隔离实测中，原 60 秒预算内定位、下载和关闭预览约用了 56 秒，下载后查找聊天框又用去约 3 秒，恢复只剩约 0.6 秒而失败，因此仅把采集预算增加至 90 秒。第 12 轮进一步确认：聊天框实际仍在原招聘页，下载自动打开的 PDF 抢走了 Worker 当前页指针；先前“关闭预览把聊天收起”的判断已被现场证据排除。结构化、消息回复及其他超时不变，取消与身份核对仍必须通过；90 秒下的真实完整采集仍待后续实测。

猎聘附件下载前记录唯一活动招聘页的完整地址，下载成功、失败或取消的收尾都先重新枚举标签页，按该地址唯一匹配后使用最新页面序号切回。页面序号不是稳定标识，不能缓存下载前的序号；切换返回地址、活动状态和原候选人姓名/CID 均需核实，之后才可探测并关闭原页附件预览。原页缺失、同地址多页、切换后地址变化或身份冲突时停止关闭，并保留下载/取消与清理错误。新开的 PDF 标签不关闭，Worker 全局新页切换规则不变。正式平台注册和日志包装回归模拟 PDF 抢走当前页及页面序号变化，验证原件返回、身份失败拒绝关闭、取消可清理且保留主错误；实际页面修复效果仍由下一轮隔离实测确认。

第 13 轮发现附件文字高约 16.8px，部分落在聊天区域顶部之外，完整浏览器视口可见并不代表可点击。猎聘附件入口预滚动现要求文字完整进入聊天可见区；通用点击仍保留大目标部分可见的支持，最终落点需受容器交集约束。

## 7. 平铺步骤规范

每个主流程文件必须能从一个顶层方法看清主要顺序。

允许：

```text
Run
  -> PrepareBrowser
  -> PreparePlatform
  -> Scan
  -> Decide
  -> Act
  -> Persist
```

不允许：

```text
Run -> PrepareBrowser -> PreparePage -> SelectPosition -> Scan -> Decide
```

后者把流程藏进多个方法深处，日志和维护都会变困难。

步骤方法可以调用下一层基础能力，但不能偷偷接管后续主流程。

## 8. 任务停止

```text
StopTask
  1. 标记用户主动停止
  2. 通知当前步骤尽快结束
  3. 等待安全点
  4. 超时后取消 Context
  5. 关闭当前详情
  6. 保存 stopped 状态
  7. 同步云端摘要
  8. 按产品规则决定是否保留浏览器窗口
```

停止任务不得直接杀死整个本地程序。

## 9. 失败处理

- 步骤失败必须带任务 ID、步骤名、平台、错误码和 trace ID。
- 找不到选择器时保留 Worker 详细诊断。
- 可重试错误按配置重试，记录当前次数。
- 连续相同错误达到阈值后停止当前任务，避免无限点击。
- 当前主动打招呼流程连续 3 个候选人出现同类错误时停止任务。
- 单个候选人最多处理 180 秒；浏览器被关闭时立即停止，详情识别失败按照统一候选人错误策略处理。
- 用户关闭浏览器与程序异常必须使用不同状态。
- 失败收尾不能覆盖用户主动停止状态。
- 未捕获 panic 也必须进入同一套失败收尾，释放 Profile、停止防睡眠并保存明确错误。
- 任务每 30 秒检查一次时间断层；休眠恢复断层超过 2 分钟时按失败停止，避免继续操作过期页面。
- 岗位开启提示音时，打招呼成功播放成功音，任务失败播放失败音。
- 任务失败通过 `/api/fail-notice` 请求云端发送邮件；正常停止只同步 stopped，避免重复邮件。
- 任务完成同步要求云端返回 `notice_sent=true`，否则最多重试三次；云端通知失败只记 warning，不把已经完成的本地任务改成失败。

## 10. 状态归属

- 真实运行状态归属 Go 本地程序。
- 网页只是控制台，刷新网页不能终止任务。
- Worker 只保存浏览器会话状态，不保存业务任务状态。
- 进程重启后根据 SQLite 恢复可展示状态；不能假装中断任务仍在运行。

## 11. 下载监听流程

```text
页面触发下载
  -> Firefox 原生下载管理
  -> pending
  -> 浏览器保存文件、同名处理并写入原生历史
  -> saved 或 failed
  -> 浏览器观察器写入本地原子快照
  -> Worker 校验并同步状态
  -> Go 每秒主动同步终态
  -> SQLite 去重保存
  -> 首次 saved 显示十秒提示
  -> 用户可打开文件、在 Finder 中定位或暂不处理
```

下载同步是平台无关流程。Worker 不反向调用 Go，也不写 SQLite；Go 不参与浏览器下载文件的实际保存。

切换下载目录时，Go 先校验绝对路径，再请求 Worker 配置；Worker 等待浏览器确认新目录后返回成功，Go 才登记为允许打开文件的目录。打开或 Finder 定位下载文件时，会解析软链接后的真实路径并再次检查目录边界。旧目录中的历史下载仍可打开，清空 GoodHR 下载记录不会删除实际文件或浏览器原生历史。

程序退出时，浏览器在关闭前将原生下载的最终状态落盘；Worker 关闭浏览器后读取最后一份快照，再删除本次临时状态目录。Go 执行最后一次同步后才停止 Worker。浏览器负责原生下载保存与取消，Worker 不再等待或另存 Playwright 管理的临时文件。

## 12. 运行组件安装流程

```text
控制台提交强类型 manifest
  -> 校验当前系统资源、HTTPS 地址和完整 SHA256
  -> 按 Node、Camoufox 顺序处理，忽略历史 OCR 资源字段
  -> 下载到临时文件并报告进度
  -> 校验 SHA256
  -> 安全解压到临时目录
  -> 原子替换目标目录，失败时恢复旧目录
  -> 保存组件版本
  -> 更新 Worker 的 Node 和 Camoufox 路径
```

Node 必须为 22 或更高。Worker 就绪检查同时验证编译入口和 `cloakbrowser` Node 依赖。安装包有额外单层目录时，运行管理器递归查找可执行文件；历史 OCR 资源不参与本次安装、校验或就绪判断。

## 13. 本地程序更新流程

```text
控制台提交下载地址和目标版本
  -> 比较当前版本
  -> 校验 HTTPS 地址和完整 SHA256
  -> 下载更新包并报告进度
  -> 校验下载文件 SHA256
  -> 安全准备 pkg 或 zip 安装器
  -> 用 macOS 默认安装方式打开
```

本地程序更新与 Node/Camoufox 运行组件更新分开，不能放进同一个管理器。

## 14. 日志和本地数据保留

- Go 和 Worker 的结构化步骤日志统一按任务编号写入岗位日志，每个岗位只保留最近 1000 条。
- 主程序和 Worker 文件日志单个最多 10MB，各保留 3 份历史文件。
- 本地任务、候选人、会话、下载和步骤摘要保留 90 天。
- 临时截图和组件下载压缩包保留最多 24 小时，程序更新包保留最多 7 天。
- 用户下载目录、浏览器 Profile、Cookie 和书签不参与自动清理。

### 前程无忧候选人列表超时

打开岗位日志或新生成的排障链接，展开失败记录的“查看浏览器排障详情”。从最近执行步骤能看到哪一步已完成，以及故障出现在加载提示、卡片读取、滚轮还是滚动后的复查。请求编号对应一次浏览器调用；同一编号出现在平台错误和任务结束记录中，表示同一次故障。

“收到响应头”说明本地程序收到了 Worker 的 HTTP 响应。连接中断时，本地程序会另外用最多 500 毫秒查询该编号的进度。没有收到进度时，Worker 是否开始执行仍未知。并行读取时，卡片下标从 0 开始，字段名和等待时间仅描述采样当时的状态。新的诊断不采集页面正文、候选人姓名或 Cookie。历史分享保留创建时的快照。

Windows x64、macOS Apple Silicon 和 Intel 共用 `internal/browser/client` 的 HTTP 诊断、`internal/platform/job51` 的列表步骤和 `worker/src/logging/request-progress.ts` 的进度记录，使用相同的 Go 和 Node API。发布时需要配套更新本地程序与 Worker。可用 `TestCandidateListFailureReachesPositionLog` 验证从平台异常到岗位日志上传，用 `TestPositionDiagnosticReplaceAndShare` 验证公开快照。

2026-11-09 验证了上述三个架构的主程序编译。macOS Apple Silicon 上用隔离的 Camoufox 读取 150 张模拟卡片，分别触发请求断开和执行超时，两次都保留了本次请求尚在等待的字段和毫秒数。Windows 与 Intel Mac 本次验证到编译，真实招聘账号的原故障仍需新版客户端复现。

### 岗位步骤超时、中断与取消

岗位日志和分享页直接展示故障环节、正在等待的动作和触发原因。同一条日志可以有多层证据。例如，候选人的总时限先到时，候选人层记录自身预算，AI 层记录当时是在等响应头、第一段有效内容，还是已经开始接收。收到的 HTTP 状态、尝试次数、耗时和已接收字节数只在对应环节采集。主动停止有独立来源，只有取消信号且发起者未知时会如实说明。

读取简历时，浏览器分别记录定位元素与读取已定位元素值，只有执行端实际报告取值超时才显示该步时限。连续读到空正文后，可从重试次数核对此前已经返回过几次空值。浏览器回执与 OCR、长截图、附件、云端同步分别保留各自的等待阶段。内置 AI 代理在接收响应头之前失败时可返回故障分类；已经开始流式转发时，通过与新版客户端协商的流事件补充中断原因。评分已得到后发生的尾段异常会说明评分是否仍可使用。历史分享保留创建时的记录，无法补出当时未采集的字段。

这些环节通过公共 Go 代码 `internal/system/failurediag` 和 `internal/flow/lifecycle` 汇总，截图阶段来自 `worker/src/browser`。Windows x64、macOS arm64 与 macOS amd64 使用同一套字段，不涉及系统专用接口。验证时分别编译三个目标，针对超时、流中断、附件及取消运行模拟故障测试，并用桌面和手机宽度核对岗位与公开日志。macOS Apple Silicon 已用真实 Camoufox 在本地模拟页验证正常正文与定位失败的两条路径，进度中仅保存动作阶段。完整显示需要配套更新本地程序、Worker、相关云端服务和控制台。

## 15. 首条真实筛选结果与教程事实

关键词拒绝和纯关键词最终判断属于筛选终态。关键词通过后仍需要 AI 最终评分时，仅发布 `preview`、`terminal=false`，不能提前完成教程；AI 最终评分返回后才发布终态。

教程事实通过已有云端接口在后台同步，每次任务最多一个请求在途。成功后不重复，失败只记录日志，后续真实终态可重试；同步有独立的 3 秒预算，不阻塞候选人流程。任务统计只持有原子同步状态的指针，该状态不进入 JSON 统计，也不改变扫描、成功、失败或跳过计数。上传证据仅有 `kind`、`phase`、`terminal`，不包含候选人资料。

此能力位于公共 `internal/flow/greeting` 和 `internal/flow/shared`，Windows、macOS Apple Silicon 与 Intel 复用相同代码，不调用系统专属能力。2026-10-15 已通过流程与云端单元测试，以及 `windows/amd64`、`darwin/arm64`、`darwin/amd64` 编译；macOS 真机运行尚未验证。定向 `go test -race` 已尝试，但当前 Windows 环境没有 GCC，无法构建 race 所需的 CGo。
