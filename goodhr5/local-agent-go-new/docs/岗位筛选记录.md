# 岗位两轮筛选记录

本地公共Go流程负责采集，四个平台继续只提供卡片、详情与动作，TypeScript Worker不处理评分或云端记录。此次没有修改平台选择器、页面动作或浏览器协议。

每次真正处理候选人创建新的UUID `attempt_id`。卡片AI预筛在并发worker现场先落盘再调用，结果不依赖主循环消费；达到招呼上限、停止或取消时，已经调用的第一轮仍保留。详情判定复用同一编号。关键词保存实际命中结果，AI分数与阈值为null；未执行两轮也保留原因，不补造评分、起止或耗时。

实际调用前保存running状态。首轮和详情评分都复用流式提前评分机制，从调用前保存running开始计时，至分数与原因完整可用结束；其中包含调用前running快照的落盘开销。完整AI输出继续在后台读取，耗时不包含并发队列、页面操作、结果保存或结构化简历尾部。正常取消/失败有可确认的起止和毫秒数；异常重启无法确认结束时刻时，仅保留原started_at，将结束和耗时留空。零分和零毫秒不会变成缺失。

SQLite迁移`007_screening_records.sql`保存独立快照和revision/acked_revision，不保存Token。每次本地修改递增完整快照版本。后台每三秒补传当前已验证账号的数据，失败保留并延迟重试；同一尝试始终使用原编号。上传期间产生新版本，旧回执只确认它实际发送的版本，不清除新结果。账号切换取消旧网络请求，不领取其他账号的队列。程序启动恢复未结束快照；已经确认的结束记录沿用90日清理，待补传记录不随普通清理删除。

云端只接收`POST /api/positions/{position_id}/screening-records`的完整快照，归属由正常登录会话及本人岗位权限确定，本地不会指定云端owner/tenant。不依赖`output_structured_resume`开关，不要求创建云端简历。每轮完整原因同时写入普通本地日志，使用该轮真实毫秒数；通过/不通过不混作网络错误。

Windows、macOS Apple Silicon和Intel使用同一份Go采集与补传代码，没有新增系统调用或原生依赖。分别检查`windows/amd64`、`darwin/arm64`、`darwin/amd64`编译；Mac安装包仍使用既有通用PKG/ZIP脚本。自动化使用真实临时SQLite与本机HTTP模型桩，不能替代真实招聘平台、真实云端账号和用户机器安装验收。
